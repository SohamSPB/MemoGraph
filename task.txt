11. Per-step heaviness and image resizing (current observations):
    - From `resource_usage.csv` on a sample trip and the stats_*.txt summaries:
        - STEP 1 (scan images) briefly spikes CPU (~90–110%) but with modest RAM, then finishes quickly.
        - STEP 2 (assign days) is light and fast.
        - STEP 3 (location resolver) is moderate CPU but stable RAM.
        - Faces/Labels/Captions/AI Captions/Species are the heaviest steps, with multi-core CPU usage and RAM increasing as MAX_IMAGE_SIZE grows:
            - ~1.3 GB peak at 256px, ~1.4 GB at 512px, ~1.9 GB at 1024px.
        - Steps 9–10 (blog + map) are lightweight.
    - Practical tuning guidelines:
        - For face detection (CNN/HOG) you can usually process small batches (2–8 images) safely; larger batches risk spikes in memory, especially on GPU.
        - For CLIP-based label/species detection and BLIP-based captioning, even 1-2 concurrent images per worker can be heavy; keep `CAPTION_PARALLEL_WORKERS` low and consider lowering `FACE_DETECTION_PARALLEL_WORKERS` or turning `MEMOGRAPH_PARALLEL_EXECUTION` off if freezes occur.
        - If the machine stalls or becomes unresponsive, reduce concurrency before reducing batch size (fewer workers first, then smaller batches).
    - Image resizing before models:
        - `face_detector.py` resizes images to CFG.MAX_IMAGE_SIZE (longest side) before running face detection.
        - `image_labeler.py`, `species_detector.py`, `caption_filler.py`, and `generate_ai_captions.py` also resize each image to CFG.MAX_IMAGE_SIZE (preserving aspect ratio) before passing it to CLIP/BLIP transforms.
        - This downsampling reduces per-image memory usage and makes it safer to handle higher-resolution photos in all model-based steps.

13. CLIP-based species prompts and current species pipeline behavior:
    - `species_detector.py` uses CLIP in a zero-shot way: the `species_prompts` dictionary defines the only species names that CLIP can choose from when filling `species_tags`.
        - If a photo contains a species (e.g. a Sparrow) that is listed in `species_prompts["birds"]`, CLIP can match against that name and we may see `"Sparrow"` in `species_tags` (subject to the confidence threshold).
        - If we never mention a species name in `species_prompts` at all, CLIP cannot output that exact name; at best it will still indicate a coarse category like `"a bird"` via `image_labeler` or via captions, but `species_detector` will not invent unseen species names.
        - If `species_prompts` were empty, `species_detector` would always return an empty list of matches and `species_tags` would remain whatever coarse text came from `image_labeler` (or blank if nothing was set earlier).
    - Recent changes to the coarse + fine species flow:
        - `image_labeler.py`:
            - Now keeps all top CLIP labels (including `"a bird"`, `"an insect"`, etc.) in `detected_objects` instead of removing them.
            - Extracts coarse species-like labels into `species_tags` as a first pass (e.g. `"a bird; a flower"`), so that CSVs always contain at least a generic indication of animals/plants present.
        - `species_detector.py`:
            - No longer wipes out existing `species_tags` on failure; it only overwrites them when it has confident CLIP-based species matches from `species_prompts`.
            - When it cannot make a confident prediction, it preserves any coarse tags already present (e.g. `"a bird"` from `image_labeler`) so information is not lost.
    - To improve true species recognition in the future:
        - Expand `species_prompts` with more realistic/common species names for your trips, or
        - Plug in specialized bird/insect/animal/plant models that take the coarse `"bird"/"insect"/"animal"/"plant"` hints from `detected_objects`/captions and then predict fine-grained species, merging those results back into `species_tags`.
        - This work is not yet implemented, but the current pipeline structure and notes here are meant to support continuing in that direction.

15. FUTURE (not yet implemented): Robustness, incremental saving, and pause/resume
    - Goals:
        - Avoid losing work when processing large batches of images (e.g. 750 photos) if a script or OS crashes mid-run.
        - Support re-running scripts as an implicit "resume" so that already-processed rows are skipped automatically.
        - Keep CSVs stable and comparable across resolutions/runs by enforcing a consistent row order.
    - Planned improvements (general pattern for heavy scripts like `face_detector`, `image_labeler`, `caption_filler`, `generate_ai_captions`, `species_detector`):
        1. Sort images deterministically at the start:
            - DONE: `image_scanner.py` now collects all image paths, sorts them by relative path, and writes `labels.csv` in that stable order.
            - All downstream scripts should preserve this ordering unless they have a deliberate reason to re-sort (e.g. face_detector’s batch-based processing, which should restore original order after parallel execution).
        2. Idempotent row processing ("skip already processed"):
            - For each script, define what it means for a row to be "done":
                - `face_detector`: `faces_detected` is `"0"` or `"1"`.
                - `image_labeler`: `detected_objects` is non-empty.
                - `caption_filler`: `caption` (and optionally `caption_samples`) is non-empty.
                - `generate_ai_captions`: `caption_ai` is non-empty.
                - `species_detector`: `species_tags` is non-empty.
            - At the beginning of each script’s main loop, skip rows that already have the target fields populated, so re-running the script naturally resumes on only the missing/empty entries.
        3. Optional explicit "done" flags:
            - Add boolean/marker columns to `labels.csv` such as `faces_done`, `labels_done`, `caption_done`, `caption_ai_done`, `species_done`.
            - Scripts would:
                - Only process rows where their `*_done` flag is false/empty.
                - Set the corresponding flag to true once a row is successfully updated.
            - This makes pause/resume behavior clearer than inferring from empty strings, at the cost of extra columns.
        4. Periodic incremental saving during long loops:
            - DONE (for captioning scripts):
                - `caption_filler.py` now:
                    - Skips rows that already have a `caption` so it can be safely re-run to resume work.
                    - Writes back to `labels.csv` incrementally:
                        - In parallel mode: after every 10 completed futures.
                        - In sequential mode: after every 10 processed rows.
                - `generate_ai_captions.py` now:
                    - Skips rows that already have `caption_ai` so it can resume where it left off.
                    - Flushes `labels.csv` after every 10 processed rows.
            - Future extension:
                - Apply the same "skip processed rows + periodic save" pattern to other heavy scripts (`face_detector`, `image_labeler`, `species_detector`) to gain the same robustness benefits.
        5. Simple pause/resume workflow:
            - With "skip processed rows" + periodic saving in place, the pause/resume story becomes:
                - Pause: if the script or OS stops, whatever has already been written to `labels.csv` is preserved.
                - Resume: re-running the same script picks up only those rows that are still empty/marked as not done.
            - No external state file is required; the CSV itself becomes the source of truth about which rows are processed.
        6. Ordering and comparability across runs:
            - Because `image_scanner` writes rows in a sorted order and downstream scripts preserve row order, resolution comparisons (e.g. `MemoGraph_256/512/1024`) remain meaningful.
            - `scripts/compare_resolutions.py` relies on `image_name` keys; stable ordering and idempotent updates help ensure that comparisons reflect real model differences rather than ordering artefacts.
    - This robustness work is deferred until after current performance/memory tuning and basic functionality are stable, but the structure here should guide future implementations.
